# ADR-0001: 不使用数据库，全部状态落 `data/` 目录

- 状态：已采纳
- 提出时间：未归档（本仓库的历史档案不虚构日期，见 `CHANGELOG.md` 头部说明）
- 相关：ADR-0005（密钥与静态加密）、`Develop_Document.md`「数据备份与迁移」

## 背景

系统的持久化状态是：服务端配置（对象存储凭据、站点设置、支付配置）、用户与 WebAuthn 凭据、分享链接、订单、优惠券、邀请码、审计日志。它们的共同特征是**量小、读多写少、结构稳定**——日志按 5000 条滚动，其余都是千级以内的集合。

引入数据库能换来的是事务与查询能力；本项目的写入模式几乎全是「整个集合读出来 → 改一处 → 整体写回」（`atomic_write` + 临时文件 rename），本就不需要事务，也没有跨集合的复合查询。

## 决定

**不引入任何数据库**（含 SQLite）。所有状态以 JSON 或 JSONL 落在 `data/` 目录，`Dockerfile` 把整个目录挂成一个 volume，迁移就是把 `data/` 复制到另一台机器。

敏感的三个文件由独立的 store 管理（`secure-store.js` / `enc-store.js`），见 ADR-0005。

## 理由

- **迁移成本是运维属性里最贵的那一项**。现状是「复制一个目录 + 保证 `secret.key` / `enc.key` 同行」，这在换机器、降级回滚、离线排查三种场景里都成立；换成数据库后，迁移要先处理版本、导出格式与权限这三件事。
- **一致性靠机制而非靠约定**：写法是「临时文件 + rename」，任何时刻 `data/` 里的 JSON 都是完整的上一次快照，不存在「写了一半」的中间态被另一个进程读到。
- **零连接、零常驻进程**：管理面板在关机状态下仍可用 `jq` 直接检查；这一点在故障排查时反复兑现过。
- **依赖数保持在 1**（`express`）。引入数据库意味着引入迁移框架，本章与之抵触。

## 备选方案（已否决）

| 方案 | 否决理由 |
| --- | --- |
| SQLite | 确实解决 `logs.jsonl` 的 5000 条滚动上限，但那是**唯一**的收益，代价是迁移形态变了；日志如需长期留存，方向是外发到日志系统，不是本地换储藏格式 |
| 外部数据库（MySQL / PostgreSQL） | 把一个单容器应用变成两容器；且在这种写入模式下它的查询能力与事务都用不上 |
| 键值库（LevelDB / Redis） | 失去「人类可读、可直接修改」这个排查属性，收益同上为零 |

## 后果与需要长期遵守的约束

1. `data/` 内文件名是**契约**：`docs-sync` 断言「文档说的数据文件」与「代码实际读写的」互相逼近，改名必须先过护栏。
2. **不要因为「某处数据量变大」就动摇**：如果将来确实出现了万级以上的集合，应该先把那一个 store 换成追加式写入，而不是整库换数据库。
3. 并发写造成的覆盖风险由「进程内单实例 + 内存缓存」承担（`config-store` 是有状态单例），因此**绝不能在多进程模式下部署**——这条约束本身应当被文档守住。

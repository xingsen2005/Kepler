# ADR-0002: 文件加密用 AES-256-GCM，不引入国密 SM4

- 状态：已采纳
- 提出时间：未归档
- 相关：`Develop_Document.md`「1.7 为何不引入 SM4 作为文件加密算法」（完整实测表）

## 背景

`enc-store.js` 负责对象存储里文件的密文形态：每条对象可以走 crypto（真加密）或 magic（伪装头）。加密发生在请求处理器里（上传时同步加密、下载时解密下发），因此**吞吐**和「是否能自证完整性」直接决定这套设计能不能成立。

曾评估把国密 SM4 作为默认算法。以下数据均为本机实测（Node v22.22.2 / Windows x64 / Ryzen 5 5600 / OpenSSL 3.5.5，32MB 随机缓冲区取三次最优，脚本可复现）。

## 决定

**维持 AES-256-GCM，不引入 SM4。**

## 理由

| 观测项 | 实测 | 含义 |
| --- | --- | --- |
| `aes-256-gcm` | 2037 MB/s | 这是「加密可以放在请求处理器里同步做」的唯一前提 |
| `sm4-ctr` | 120 MB/s | **慢 17 倍**，最大的约束 |
| `sm4-cbc` | 114 MB/s | 换分组模式救不了 |
| Node 的 SM4 模式清单 | `sm4`、`sm4-cbc`、`sm4-cfb`、`sm4-ctr`、`sm4-ecb`、`sm4-ofb` | **没有 `sm4-gcm` / `sm4-ccm`**，直白地说：拿不到 AEAD |
| HMAC-SHA256 vs HMAC-SM3 | 2025 MB/s vs 239 MB/s | 「SM4 + SM3」还要再叠一层慢 MAC |
| SM4 的 IV | **只接受 16 字节**（传 12 直接抛 `Invalid initialization vector`） | 现有 IV 约定是 12 字节，得参数化 |

两个硬伤：**第一，没有 AEAD**。现有的逐段 `authTag` 校验、每段独立 IV、可 seek 解密这三样东西都是 `crypto` 模块给的，换成 SM4 就得自己搭 CTR + HMAC 的 encrypt-then-MAC——而自建 AEAD 的 bug 是**不可回滚**的：密文一旦用错算法写进对象存储，回来改算法时那些数据已经无法自证对错。**第二，慢一个数量级**，会让「同步加密」这个隐含前提失效。

需要说明的是：这不是在否定国密，而是在 Node 当前形态下，它在我们的关键路径上两样东西都给不了。

## 备选方案（已否决）

| 方案 | 否决理由 |
| --- | --- |
| `sm4-cbc` + HMAC-SM3 自建 AEAD | 自建 MAC 组合，失败模式下无法事后区分「算法写错」与「数据损坏」 |
| SM4 仅用于冷数据、AES 用于热数据 | 两套密文形态 ⇒ 解密判据分裂；元数据里任何一个遗漏分支都会在很久之后才暴露 |

## 后果与需要长期遵守的约束

1. 算法选择写在密文头（`COSCENC01` 魔数 + 版本），将来若真要支持别的算法，**先扩展密文头，再谈算法**，不要让读取方靠猜。
2. 不要把这个结论复述成「SM4 不安全」——这里没做密码学层面的评价，做出判断的是「有没有 AEAD」与「够不够快」两个工程事实。
3. 如将来 Node 原生提供 `sm4-gcm`，且吞吐进入同一量级，本 ADR 应当被新的 ADR **取代**而不是删掉（保留被取代记录）。

# ADR-0005: 静态加密用两把主密钥，元数据预留 `keyId`

- 状态：已采纳（`keyId` 预留于 Round 66，版本 `1.9.2`）
- 提出时间：未归档
- 相关：`server/secure-store.js`、`server/enc-store.js`、`data/secret.key` / `data/enc.key` / `data/enc-meta.json`

## 背景

两套数据被静态加密，且刻意用**两把不同的主密钥**：

| 数据 | 密钥 | 元数据 |
| --- | --- | --- |
| 服务端配置（含对象存储凭据、SMTP 口令） | `secret.key` | 密文头自带版本号（`ENC_FLAG` + `ENC_VERSION`） |
| 上传到对象存储的文件 | `enc.key` | `enc-meta.json`（每条记录含 mode / IV / 段信息） |

分离的意义是「配置泄露不牵连云上数据」；代价是**两把都必须备份**，`Develop_Document.md` 明确写着「只备份其中一个等于没备份」。

## 决定

维持双密钥结构，并额外做一件便宜的准备性改造：**给 `enc-meta.json` 的每条记录盖一个 `keyId`（当前恒为 1）**，密文格式一个字节都不动。

## 理由

泄露后的现实操作是「全量下载 → 全量重加密 → 全量重传」，全程停机、双倍流量。之所以只能这么重，根子不在重传，而在**元数据里没有任何东西记录这条密文是用哪把密钥加的**——于是「换密钥」和「把老数据识别出来」变成了同一个问题。

`keyId` 让这两件事分开：将来轮换时，新数据用 `keyId=2` 写，老数据仍按 1 解，存量不必先全量重写。这是典型的「用 1% 成本买 10 倍选择权」。

实现上有两个刻意的点：

1. **写入收敛到唯一实现点 `stampKeyId()`**（`enc-store.js`）。元数据有四个生产点（直传 crypto / 直传 magic / 分片 crypto / 分片 magic），逐个手写字面量将来加第五种形态必然漏，而漏掉的表现要到**真正轮换那天**才炸。
2. **老记录由 `keyIdOf()` 按 1 解释**，不写迁移脚本。没有 `keyId` 的记录就是「轮换之前写的」，语义正好。

## 备选方案（已否决）

| 方案 | 否决理由 |
| --- | --- |
| 现在就实现完整轮换（多密钥并存 + 后台重加密） | 收益要到「真泄露那天」才兑现，而成本是停机之外的复杂 ceremony；先把「能不能认出用哪把密钥」这件事准备好就够 |
| 给每条记录记时间戳、按时间推断密钥版本 | 时间不等于密钥版本：一次手动轮换可以让同一分钟内存在两种记录，`keyId` 才是直接表达 |
| 把 `keyId` 写进密文体 | 要动密文格式 ⇒ 存量数据全部需要重写，正是我们想避免的前置条件 |

## 后果与需要长期遵守的约束

1. `keyId` 是**密之外**的东西：它必须在只读模式下也能读到，因此永远不要把它挪进密文内部。
2. 新增任何「产生一条 `enc-meta` 记录」的代码路径，**必须走 `stampKeyId()`**，而不是自己拼对象字面量。
3. 「轮换」本身没有实现，文档里应当继续保持诚实（而不是写成「已支持」）。本 ADR 记录的是让将来可轮换，**不是**已经可轮换。

# ADR-0004: 前端零构建 —— 原生 ESM、无打包器、无框架

- 状态：已采纳
- 提出时间：未归档
- 相关：`public/js/`（原生 ES Module）、`jsconfig.json`、`tests/frontend.test.js`

## 背景

管理界面有几十个前端模块，全部是浏览器直接加载的原生 ES Module：没有 TypeScript、没有打包器、没有框架，`index.html` 里 `<script type="module">` 直接引用。

这个形态让「改一行前端代码」的成本等于「改一行服务端代码」：不需要 `npm run build`，不会出现「源码改了但产物没更新」，也不会有 sourcemap 与产物之间的那层不可见差异。

## 决定

**维持零构建。** 不引入打包器、不引入框架、不在浏览器侧引入类型检查工具链。

类型这块用最小代价补——新增 `jsconfig.json`，把 `checkJs` 保持 **关闭**，需要类型检查的文件在**文件头**单独写 `// @ts-check`，逐文件推进。

## 理由

- 「零构建」不是偷懒，而是一个**可靠的属性**：它使部署形态从「源码 + 产物」退回「只有源码」。`deploy.sh` 只需 `npm ci` 加一个 Node 进程，镜像也不需要 Node builder 阶段。
- CSP 不允许内联脚本（`server/security.js`），原生模块契合这套约束；打包器产出通常会引入 inline bootstrap 与 eval 风格的热更新代码，与之相斥。
- **引入框架的收益与代价不成比例**：界面是「表格 + 弹窗 + 卡片的 CRUD」，状态分散在无依赖的模块里且以服务端渲染为主（`share-routes` 直接输出 HTML）；换成 SPA 会同时丢掉服务端的那些判断。
- 把 `checkJs` 全局打开会在没有 JSDoc 的文件里刷出成片噪音，噪音会让人关掉它——所以**按文件推进**而不是全仓打开。这是「渐进 adopted」能成立的唯一形态。

## 备选方案（已否决）

| 方案 | 否决理由 |
| --- | --- |
| 引入 Vue / React | 破坏零构建；需要打包步骤或运行时 CDN 依赖（后者与 CSP、离线部署都冲突） |
| esbuild / Vite 等打包器 | 部署从「复制源码」变成「源码 + 产物」，且必须回答「产物要不要进库」 |
| 全量 TypeScript | 需要编译产物 ⇒ 回到上一个否决项；`@ts-check` 逐文件推进能达到 90% 的收益 |

## 后果与需要长期遵守的约束

1. 前端模块必须**能被 Node 直接解析**（`frontend.test.js` 逐个 `import` 并做语法检查），因此不要引入浏览器专有语法糖或 import 断言。
2. 新增前端模块会改变计数（`README` 的「N 个文件 / N 个前端模块」、`frontend.test.js` 的模块列表），改动两边都得跟上。
3. 模块多了以后最先痛的地方是**跳转与补全**，`jsconfig.json` 就是专门为此补的；如果将来某处真的需要类型，就给那个文件加 `// @ts-check`，不要整体开。

# ADR-0007: 不引入 MasterCard / Visa 等银行卡支付

- 状态：已采纳
- 提出时间：未归档
- 相关：`server/payment-gateway.js`、`server/payment-rules.js`、`server/payment-providers.js`

## 背景

现有支付接入是**三家直连**：支付宝、微信支付、PayPal（`payment-gateway.js` 的 `createCharge()` 只回一个收银台跳转链接或二维码，形如 `{ ok, payUrl | qrCode }`）。它们共同的特点是：**全部为跳转式收银台**——卡号、有效期、CVV 从来不经过本站。

曾评估再接入 MasterCard / Visa。

## 决定

**不引入。** 不论从合规、协议还是接第一方直连资格的角度看，收益都与投入不成比例。

## 理由

1. **合规门槛不是「接个 SDK 就自动合规」**：一旦自己收集、传输或存储卡号（PAN）、有效期、CVV，就进入 **PCI-DSS 的合规范围**，随之而来的是网络分段、日志脱敏、年度评估这一整套。轻量级的单机部署形态与它不相容。
2. **卡组织强要求身份认证**（3DS 等）：需要前端集成 iframe / 重定向的挑战流程，后端维护验证会话状态。现有 `createCharge()` 只是「拿到一个跳转地址」，没有处理挑战所需的异步状态机。
3. **资金术语与交付模型不匹配**：`payment-rules.js` 走「下单 → 回调 → 发货」的一次性模型，没有「预授权冻结 / 部分捕获 / 长周期状态轮询」；强行接入会出现「已发货但资金未结算」「退款状态不同步」这两类错账。
4. **回调面膨胀**：信用卡网关推送数十种事件类型（成功、失败、部分退款、争议、仲裁结果）。若回调路由没实现严格的幂等与签名验签，极易重复发货。
5. **第一方直连资格**：Visa / MasterCard 只对持牌机构或大型商户开放直连，必须走聚合网关（Stripe、Adyen、Checkout.com 等）。`payment-providers.js` 现在定义的是三家平台直连所需的凭据字段（`appId` / `privateKey` / `mchId` / `apiV3Key` / `clientId` / `clientSecret` / `merchantId`），没有「SDK 托管模式」或「前端 Token 化」这套接口，得重构网关层才能适配 PaymentIntent / Customer / Source 这类对象模型。

## 备选方案（已否决）

| 方案 | 否决理由 |
| --- | --- |
| 通过聚合网关间接接入 | 仍然要 3DS 挑战与异步状态机（第 2/3 条不因换网关而消失），且把「多一层 PCI 范围审查」换成「多一层账单与对账复杂性」 |
| 只支持借记卡绕过 3DS | 持卡行的规则不由我方决定，且实际覆盖面极低 |

## 后果与需要长期遵守的约束

1. **不允许在服务端或前端处理卡信息**：这一条应由代码审查与文档口径共同守住，而不是靠约定。
2. 若将来确有需要，**先做**的是引入聚合网关的对象模型与完整的事件幂等层；那是一个独立轮次，不是「再加一个支付渠道」。
3. 现有支付 audit 与退款回退逻辑（优惠券只回退非无门槛券）建立在「一次性扣款 + 一次性退款」的模型上，任何新支付方式都必须先回答它与这个模型是否相容。

# ADR-0003: 移除自签名证书，只认运维自备的真实证书

- 状态：已采纳（Round 49，版本 `1.7.1`）
- 提出时间：未归档
- 相关：`server/tls-cert.js`、`deploy.sh` 的 `--tls file|none`、环境变量 `TLS_CERT_FILE` / `TLS_KEY_FILE`

## 背景

早期版本在拿不到证书时会现场生成一张自签名证书，让内置 HTTPS 端口（缺省 `data/tls/`）照常起来，`README` 里甚至印着「浏览器打开 `https://127.0.0.1:3443`（自签名证书）」。

这么做在本机上看着是「站点起来了」，但用户拿到的实际是：浏览器地址栏一行「不安全」，以及一行大多数人看不懂的证书警告。

## 决定

**删除自签名证书这条路径**（连同 `selfsigned` 依赖）。HTTPS 只在运维提供了真实证书时才监听；没有证书就**只跑 HTTP**，而且此时不能 301 到没人监听的 HTTPS 端口。

证书来源只有两个：`--tls file`（自备证书，`TLS_CERT_FILE` / `TLS_KEY_FILE`）与 ACME（`--tls zerossl|litessl`，需在 kr.io / zerossl.io 凭据具备的前提下）。**ACME 失败就是失败，不再回退到自签名。**

WebDAV 依赖 TLS（`webdav-server` 只跑 HTTPS），因此缺证书时它不起，且原因要能传到界面（这就是 `getTlsError()` 的存在理由：把「缺文件」与「启动中」区分开）。

## 理由

- **自签名证书换不来任何东西，只换来一个假的「已加密」观感**。它不能让浏览器认为站点安全，也不能让 **WebAuthn / WebAuthn 安全上下文**这类 API 可用。用户为一个「不再显示 http:// 的红字」付出的是：每次访问一个新的一次性警告 + 无从证明服务器身份。
- 比起「起不来」，**「起来但是不安全」危害更大**：前者用户立刻知道要修，后者用户会一直用下去，并在某天把站点的敏感操作（WebAuthn、密钥）建立在这张证书上。

## 备选方案（已否决）

| 方案 | 否决理由 |
| --- | --- |
| 保留自签名但默认关闭 | 监听器仍在代码里；一旦某个部署路径被触发，同样的假安全又回来——这就是我们删掉整条路径而不是加开关的原因 |
| `--tls none` 的基础上仍然打印 HTTPS 地址 | 界面宣称的服务形态与实际不符，`README` 曾长期印着这行误导性端口 |

## 后果与需要长期遵守的约束

1. 源码、依赖、`deploy.sh` 里**都不允许再出现** `selfsigned` 相关实现（有多条静态护栏盯着）。
2. 反代场景的 301 目标是**对外**端口（`PUBLIC_HTTPS_PORT`，缺省 443），而不是内置监听端口——旧实现的 bug 正是把访客送去内置那张不被信任的证书。
3. 「证书没配好」必须是**可诊断的**（哪个文件缺、证书与私钥是否配套），不允许笼统报一句「TLS 不可用」。
